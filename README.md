## Хэсэг A: Category-Partition (гараар) - шилжүүлгийн функц

Тестлэгдэх функц: `POST /transfer { from, to, amount, currency }`. Амжилт `201 {"result":"OK"}`, оролтын алдаа `200 {"result":"ERROR_..."}`.

### Олон алдааны давуу эрэмбэ

Нэг хүсэлтэд хэд хэдэн алдаа зэрэг байвал **from → to → amount** дарааллаар шалгана гэж тогтоосон: `ERROR_NO_FROM` → `ERROR_FROZEN` → `ERROR_NO_TO` → `ERROR_SAME_ACCOUNT` → `ERROR_BAD_AMOUNT` → `ERROR_INSUFFICIENT` → `ERROR_LIMIT`. Үндэслэл: эхлээд оролцогч дансууд байгаа эсэх, идэвхтэй эсэхийг (from, дараа нь to) шалгана, учир нь дүнг үлдэгдэл/лимиттэй харьцуулахад from данс заавал хэрэгтэй; дүнгийн хувьд оролт өөрөө буруу эсэхийг (`amount <= 0`) дансны төлөвөөс хамаарсан шалгалтаас (үлдэгдэл, дараа нь лимит) өмнө шалгана.

### A1. Сонголт ба төлөөлөх утгууд

| Параметр / сонголт | Төлөөлөх утга | Тайлбар |
|---|---|---|
| **from** | `Valid` | байгаа, царцаагдаагүй данс |
| | `Frozen` | байгаа боловч царцаагдсан данс |
| | `Missing` | огт байхгүй дансны ID |
| **to** | `Valid` | байгаа данс, from-оос өөр |
| | `Missing` | байхгүй дансны ID |
| | `SameAsFrom` | from-той ижил ID |
| **amount** | `Normal` | 0 < amount, үлдэгдэл ба лимитийн дотор |
| | `ExactBalance` | amount яг дансны үлдэгдэлтэй тэнцүү (хязгаарын утга) |
| | `Zero` | amount = 0 |
| | `Negative` | amount < 0 |
| | `OverBalance` | үлдэгдлээс их, лимитийн дотор |
| | `OverLimit` | үлдэгдлийн дотор, өдрийн лимитээс их |
| | `OverOnlyAfterConversion` | тоон утгаараа үлдэгдлээс бага, харин хөрвүүлсний дараа үлдэгдлээс их |
| **currency** | `Same` | дансны валюттай ижил |
| | `Different` | дансны валютаас өөр, ханшаар хөрвүүлэгдэнэ |

**Далд орчны сонголт.** Үлдэгдэл, өдрийн лимитийн хэрэглээ, ханш нь хүсэлтийн талбар биш, системийн төлөв. Иймд тэдгээрийг тусдаа параметр болгохгүй, `amount`-ийн утгуудаар (`OverBalance`, `OverLimit`, `OverOnlyAfterConversion`) илэрхийлсэн: тест бүр өөрийн setup-аар үлдэгдэл, лимитийг тохируулж тухайн ангийг үүсгэнэ. Тусдаа сонголт болгож нэмсэн зүйл бол "хөрвүүлсний дараа" шалгах дүрэм (`OverOnlyAfterConversion`), учир нь тодорхойлолт үлдэгдэл, лимитийг хөрвүүлсний дараах дүнгээр шалгана гэж заасан.

### A2. Хязгаарлалтууд

| Утга | Тэмдэглэгээ | Үндэслэл |
|---|---|---|
| from = `Frozen` | **[ERROR]** | `ERROR_FROZEN` буцаах ёстой, өөр утгатай хослуулбал алдаа бусдыг нууна |
| from = `Missing` | **[ERROR]** | `ERROR_NO_FROM` |
| to = `Missing` | **[ERROR]** | `ERROR_NO_TO` |
| to = `SameAsFrom` | **[ERROR]** | `ERROR_SAME_ACCOUNT` |
| amount = `Zero`, `Negative` | **[ERROR]** | `amount <= 0` буюу `ERROR_BAD_AMOUNT` |
| amount = `OverBalance` | **[ERROR]** | `ERROR_INSUFFICIENT` |
| amount = `OverLimit` | **[ERROR]** | `ERROR_LIMIT` |
| amount = `OverOnlyAfterConversion` | **[ERROR]** + **[IF currency = Different]** | `ERROR_INSUFFICIENT` боловч зөвхөн валют өөр үед утгатай: ижил валютад "хөрвүүлсний дараа" гэж байхгүй |
| amount = `ExactBalance` | **[SINGLE]** | хязгаарын утга, нэг удаа шалгахад хангалттай (үлдэгдэл бүрэн дуусгах нь ердийн амжилттай шилжүүлэг) |
| from = `Missing` үед amount-ийн `ExactBalance`/`OverBalance`/`OverLimit`/`OverOnlyAfterConversion` | **[IF from != Missing]** | from данс байхгүй бол үлдэгдэл, лимит, хөрвүүлэлт байхгүй тул эдгээр дүн утгагүй |
| from = `Missing` үед to = `SameAsFrom` | **[IF from != Missing]** | from байхгүй бол "to = from" гэж харьцуулах зүйл байхгүй |

### "N -> M" тооцоо

- Бүрэн олонлог: 3 (from) x 3 (to) x 7 (amount) x 2 (currency) = **126**
- Хязгаарлалтын дараа: [ERROR] утга бүр өөрөө ганц тест болно (бусад параметр хүчинтэй төлөөлөгчтэй): from 2 + to 2 + amount 4 (`Zero`, `Negative`, `OverBalance`, `OverLimit`) + `OverOnlyAfterConversion` 1 (currency зөвхөн `Different`) = **9**; хүчинтэй хослол: from=Valid, to=Valid, amount=Normal, currency 2 утга = **2**; [SINGLE] `ExactBalance` = **1**.
- Дүн: 9 + 2 + 1 = 12, өөрөөр хэлбэл **126 -> 12**.

## Хэсэг B: PICT - pairwise covering array

PICT анхдагчаар ажиллах бүрт ижил үр дүн өгдөг (`/r` хэрэглээгүй). Model файлуудын тайлбарыг зөвхөн ASCII (англи) тэмдэгтээр бичсэн.

### B1. Лекцийн браузерын жишээ (`browser.model`)

| Ажиллуулалт | Файл | Мөрийн тоо |
|---|---|---|
| Бүрэн олонлог (3 x 3 x 2 x 2 x 2 x 2) | - | 144 |
| 2-way (pairwise) | `results/browser-2way.txt` | **10** |
| 3-way (`/o:3`) | `results/browser-3way.txt` | **20** |

**Greedy-гийн тайлбар.** Лекц дээр гараар 9 мөрөнд багтаасан бол PICT 10 мөр өгсөн. 9 нь онолын доод хязгаар (Content x Cookies = 3 x 3 = 9 хос бүр тусдаа мөр шаардана), харин PICT greedy алгоритмтай: алхам бүрт одоогоор хамрагдаагүй хосуудыг хамгийн их хамарсан мөрийг сонгоод, өмнөх сонголтоо буцааж өөрчилдөггүй, тиймээс хамгийн цөөн мөрийг ЗААВАЛ өгдөггүй. Үүний хариуд хурдан бөгөөд бүх хосыг хамрах баталгаатай (шалгахад 2-way файлд хамрагдаагүй хос 0). 3-way 20 мөр нь бүрэн олонлог 144-ийн ойролцоогоор 14%, онолын доод хязгаар 3 x 3 x 2 = 18-аас 2-оор их.

### B2. Шилжүүлгийн model-ууд

Model файлууд репод байгаа: `transfer-nc.model` (хязгаарлалтгүй), `transfer.model` (A2-ын боломжгүй хослолын хязгаарлалттай), `transfer-neg.model` ([ERROR] утгууд `~`-тэй).

| Хувилбар | Файл | Мөрийн тоо | Happy path мөр (бүх утга хүчинтэй) | Нэг мөрөнд хамгийн их алдаа | 2+ алдаатай мөр |
|---|---|---|---|---|---|
| Хязгаарлалтгүй | `results/transfer-nc.txt` | **22** | **0** | 3 | 17 |
| Хязгаарлалттай (A2) | `results/transfer.txt` | **21** | **0** | 3 | 14 |
| Сөрөг утгатай (`~`) | `results/transfer-neg.txt` | **21** | **4** | 1 | 0 |

Бүрэн олонлог 126, PICT 22 / 21 / 21 мөр.

**Гаралтаас харсан зүйл.**
- Энгийн утгатай хоёр хувилбар (`transfer-nc`, `transfer`) happy path мөр **огт гаргаагүй**: алдааны утга олон (from 2, to 2, amount 6) тул хос бүрийг хамрахдаа алдааны утгуудыг хооронд нь хослуулж, бүх мөр дор хаяж нэг алдаатай болсон.
- `transfer-nc` ба `transfer`-д нэг мөрөнд 3 хүртэл алдаа орсон. Ийм мөр юуг шалгаж байгаа нь тодорхойгүй: хариуд `ERROR_FROZEN` ирвэл to, amount-ын алдаа шалгагдсан эсэх нь мэдэгдэхгүй (error masking). Oracle нь зөвхөн А хэсгийн давуу эрэмбээс (from → to → amount) гарна.
- Хязгаарлалтгүй `transfer-nc` дотор боломжгүй мөр бий (жишээ нь `OverOnlyAfterConversion` + `Same`, `from=Missing` + `SameAsFrom`); `transfer.model`-ийн хязгаарлалт тэдгээрийг арилгасан (`results/transfer.txt` дотор тийм мөр 0).
- `~` хэрэглэсэн `transfer-neg` 4 happy path мөр гаргаж, нэг мөрөнд ХАМГИЙН ИХДЭЭ ГАНЦ алдаа оруулсан тул мөр бүрийн oracle тодорхой.

**`~` хэрэглэхэд A2-ын хязгаарлалт хэрэгтэй юу?** Алдааг нуух (masking) болон "from=Missing үед балансаас хамаарсан дүн утгагүй" гэсэн хязгаарлалтууд `~`-тэй үед автоматаар хангагддаг, учир нь нэг мөрөнд ганц сөрөг утга орно. Харин нэг хязгаарлалт хэрэгтэй хэвээр: `IF [Amount] = "OverOnlyAfterConversion" THEN [Currency] = "Different"` - үүнийг хасаж үзэхэд PICT `~OverOnlyAfterConversion` + `Same` гэсэн боломжгүй мөр гаргасан. Иймд `transfer-neg.model` дотор энэ ганц хязгаарлалтыг үлдээсэн.

### B2b. Гаралтаас бодит тест кейс

Нийтлэг setup (дансны ID бүр тест бүрт өвөрмөц, жишээ нь `A_TC1`): from данс `A_TCn` = 1000 USD, өдрийн үлдэгдэл лимит 5000 USD; to данс `B_TCn` идэвхтэй; ханш 1 EUR = 2 USD.

| Тест | PICT мөр (файл) | Setup | Оролт | Oracle |
|---|---|---|---|---|
| TC1 happy path | `Valid Valid Normal Same` (`transfer-neg.txt`) | `A_TC1`: 1000 USD, идэвхтэй; `B_TC1`: идэвхтэй | `{from:"A_TC1", to:"B_TC1", amount:100, currency:"USD"}` | `201`, `result="OK"` |
| TC2 нэг алдаатай мөр | `Valid Valid ~OverBalance Same` (`transfer-neg.txt`) | TC1-тэй ижил | `{from:"A_TC2", to:"B_TC2", amount:1500, currency:"USD"}` | `200`, `result="ERROR_INSUFFICIENT"` |
| TC3 нэг алдаатай мөр, хөрвүүлэлт | `Valid Valid ~OverOnlyAfterConversion Different` (`transfer-neg.txt`) | TC1-тэй ижил | `{from:"A_TC3", to:"B_TC3", amount:600, currency:"EUR"}` (600 EUR = 1200 USD > 1000 USD) | `200`, `result="ERROR_INSUFFICIENT"` |
| TC4 олон алдаатай мөр | `Frozen Missing Negative Different` (`transfer.txt`) | `A_TC4`: царцаагдсан; `B_TC4_GHOST` үүсгэхгүй | `{from:"A_TC4", to:"B_TC4_GHOST", amount:-5, currency:"EUR"}` | `200`, `result="ERROR_FROZEN"` (давуу эрэмб: from нь to ба amount-аас өмнө шалгагдана) |

TC4-ийн oracle нь PICT-ээс бус А хэсгийн давуу эрэмбээс гарсан: тодорхойлолт аль алдаа буцахыг заагаагүй тул энэ бол миний тогтоосон таамаглал, код байхгүй тул баталгаажуулах боломжгүй.

### B3. Гараар (A3) ба PICT-ийн харьцуулалт

| | Гараар (A3, 15 спецификаци) | PICT (`transfer-neg`, 21 мөр) |
|---|---|---|
| Алдааны семантик | Спец бүрд хүлээгдэх ERROR тодорхой, давхар нөхцөл ба давуу эрэмбийг шууд шалгана | Зөвхөн оролтын хослол гаргана, oracle-гүй; олон алдаатай мөрийн oracle-ийг гараар нөхөх хэрэгтэй |
| Хосын хамралт | Баталгаагүй: утга бүр ядаж нэг удаа орсон ч, жишээ нь `Different` валют бүх алдааны ангитай хослосон эсэх мэдэгдэхгүй | Хос бүр хамрагдсан гэсэн баталгаатай (хязгаарлалтын хүрээнд) |
| Ажлын хэмжээ | Сонголт, хязгаарлалтыг бүгдийг гараар бодно | Сонголт тодорхойлогдсоны дараа секундэд гарна; model-ийг өөрчлөхөд тоо шууд шинэчлэгдэнэ |
| Эрсдэл | Хүний алдаа, мартсан хослол | Greedy тул хамгийн цөөн биш; хязгаарлалтыг буруу бичвэл PICT алдаа өгөлгүй өөр мөр гаргаж болно, иймд гаралтыг заавал шалгана |

Алдааны семантикийг гараар хийсэн хүснэгт илүү сайн барьдаг, учир нь "ямар алдаа буцах вэ" гэдэг нь тестлэгчийн ойлголтоос гардаг. Хосын хамралтыг PICT баталгаажуулдаг. Практикт хоёрыг хослуулна: гараар сонголт, [ERROR] ангийг тодорхойлж, PICT-д `~`-тэй model болгон өгч хосын хамралтыг автоматжуулна.

## Дүгнэлт

Category-partition нь тестлэгчийг параметрүүдийг нэрлэж, утгыг ангилж, "ямар хослол боломжгүй вэ" гэж бодоход хүргэдэг; PICT нь тэр бодлын үр дүнг (model-ийг) хурдан бөгөөд хосын хамралтын баталгаатай тест болгодог. Хамгийн их бодол шаардсан алхам нь A2: ямар утга [ERROR], ямар нь [SINGLE], ямар хослол боломжгүйг шийдэх, учир нь тэндээс 126 хослол 12 болж багассан. Хамгийн гэнэтийн нээлт нь `~`-гүй model нэг ч happy path мөр гаргаагүй, мөр бүрд 3 хүртэл алдаа хольсон явдал: алдааны утга олон үед PICT тэдгээрийг хооронд нь хослуулах нь хос хамралтад "зөв" боловч тест болгоход oracle нь тодорхойгүй болно. `~` нь үүнийг засаж, 4 happy path мөр, мөр бүрд ганц алдаа өгсөн. PICT greedy тул лекцийн 9 мөрийн оронд 10 мөр гарсан нь "хамгийн цөөн" нь баталгаа биш, "бүх хос хамрагдсан" нь баталгаа гэдгийг харуулсан. Гараар хийсэн хүснэгт алдааны давуу эрэмбийг (from → to → amount) тодорхой гаргасан бол PICT-ийн олон алдаатай мөр тэр давуу эрэмбээс л oracle авна, өөрөөр хэлбэл PICT нь дизайныг орлохгүй, нөхөж өгдөг. Код байхгүй тул давуу эрэмбийг бодит системээр баталгаажуулах боломжгүй, энэ нь миний таамаглал хэвээр үлдэнэ. Дараагийн удаа model-оо гараар бичсэнийхээ дараа заавал нэг хязгаарлалт бүрийг хасаж, мөрийн тоо яаж өөрчлөгдөхийг шалгаж, хязгаарлалт үнэхээр хэрэгтэй эсэхийг батлах болно.
